# askjamie-brg02-starbucks

## Project identity

- **Suite:** AskJamie / BrandGuard
- **Project:** GPT-BRG02, OKHP3 BrandGuard for Starbucks
- **Type:** Content and knowledge repository for an intended Custom GPT brand-compliance monitor
- **Repository:** https://github.com/OKHP3/askjamie-brg02-starbucks
- **Notion anchor:** https://app.notion.com/p/14956d6e37db4d76a177173bfd96af74
- **Current status:** Partial and content-focused. The knowledge corpus is populated, while prompts, evaluations, and release outputs remain scaffolded but empty. A PowerShell technology-drift check and scheduled GitHub Actions maintenance workflow now exist, but no runnable application or release process is present in this repository.

## Mission and vision

- **Confirmed mission:** Maintain version-controlled prompts, Starbucks knowledge packs, evaluation material, and supporting cross-links for the GPT-BRG02 BrandGuard system.
- **Inferred vision:** Keep a single content source aligned across the repository, a web or lens surface, a ChatGPT Project, a Custom GPT, and Notion. This is described as an intended hybrid workflow, not a verified deployment guarantee.
- **Primary users:** The repository maintainer and operators of the BrandGuard system. Downstream users are intended to receive Starbucks brand-consistency guidance. This audience is inferred from the project documentation.

## Scope and boundaries

- This is a documentation and binary knowledge-pack repository, not an application codebase.
- The repository does not currently contain a frontend, backend, package manifest, source corpus, prompt implementation, evaluation suite, build script, or deployment script. It does contain maintenance automation for checking the Replit Nix channel.
- Treat official Starbucks sources as authoritative for current company details. The repository knowledge files are reference material and may become stale.
- Do not invent brand standards, current facts, product availability, legal conclusions, or production guarantees from these files alone.
- Do not modify application code, dependencies, generated artifacts, secrets, CI behavior, or unrelated repository content as part of guidance maintenance.

## Repository structure

- `knowledge/`: 17 numbered Starbucks knowledge topics. Each topic currently has `v01a` and `v01d` DOCX and PDF files, for 34 DOCX files and 34 PDF files. The meaning of the revision suffixes is not documented here, so preserve both variants unless an owner provides a retention rule.
- `README.md`: project purpose, intended hybrid workflow, and external cross-links.
- `replit.md`: confirms that the repository is not a runnable application and records the intended directory map.
- `gpt_manifest.yaml`: project metadata. It is currently inconsistent with this repository because it names GPT-BRG03 and Brooks Running. Treat it as stale until corrected by the project owner.
- `src/`, `prompts/`, `eval/`, `tests/`, `build/`, `rag-source/`, `releases/`, `site/`, `web/`, and `assets/`: placeholder directories containing only `.gitkeep` files.
- `ops/check-technology-updates.ps1`: maintenance script that checks the Replit Nix channel against the latest NixOS stable release.
- `docs/technology-inventory.md`: evidence-based inventory of repository formats and maintenance tooling.
- `.github/workflows/technology-drift.yml`: scheduled and manually triggered maintenance workflow that reports detected Nix-channel drift through GitHub Issues.
- `.github/dependabot.yml`: dependency-update configuration for GitHub Actions.
- `.agents/skills/`: repository-local agent skills. Read their individual `SKILL.md` files before using or changing those skills.
- `CLAUDE.md`: delegates to this file with `@AGENTS.md`.

## Intended workflow

The documented workflow is:

1. Add or revise source material and prompt assets when those directories are implemented.
2. Compile or prepare low-count upload packs in `build/` when a verified build process exists.
3. Upload approved packs to the Custom GPT or ChatGPT Project as appropriate.
4. Record behavior-changing releases in `CHANGELOG.md`.

Only the first and last steps are currently representable in the repository. No compilation or upload command is defined or verified.

## Technology and validation

- No application language, runtime, dependency manager, package manifest, or application entry point is present. PowerShell is used only for maintenance automation.
- `.replit` contains Replit agent and Nix channel settings but no run command.
- No build, test, lint, deployment, or release-packaging command is currently verified. The maintenance workflow is the only verified automation path.
- Useful read-only checks are `git status --short --branch`, `git log --oneline`, `git ls-files`, and `pdfinfo` for PDF metadata when available.
- For knowledge-pack changes, verify filenames, topic numbering, paired DOCX/PDF presence, and readable metadata. Do not claim semantic equivalence between DOCX and PDF without inspecting both.

## Change conventions

- Preserve the `BRG02-KNOW##-Descriptive-Topic-v##[letter]` naming pattern for knowledge files.
- Keep standalone punchy lines intact when editing project prose.
- Do not use em dash punctuation in generated content.
- Use concise, evidence-based documentation. Mark conclusions as confirmed, inferred, or unknown when that distinction matters.
- Preserve existing user changes and avoid destructive version-control commands.
- Keep binary knowledge files paired and traceable. If a source or provenance record is unavailable, record that limitation rather than fabricating one.
- Use a branch with the `codex/` prefix for agent-created branches unless the owner specifies another strategy.

- **Important:** `README.md` describes prompts, evaluations, and RAG-ready markdown compilations, but the current tree contains no populated prompt or evaluation files and the knowledge corpus is DOCX/PDF rather than markdown. Its opening link table also conflicts with the later canonical-link section.
- **Important:** `docs/technology-inventory.md`, `.github/workflows/technology-drift.yml`, and `ops/check-technology-updates.ps1` document and implement maintenance automation, not application or release tooling.
- **Unknown:** Which revision suffix is authoritative, whether the `v01a` and `v01d` pairs are drafts or releases, and which external link is the source of truth for each surface.
- **Unknown:** Whether the current knowledge files have been approved for Custom GPT upload or are still research drafts.
- **Optional follow-up:** Add provenance, approval state, and a verified packaging workflow before treating this repository as release-ready.
